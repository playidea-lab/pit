# PIT Overview

> **pit (Product / Idea Tracker)** 의 프로젝트 정의, 문제, 가치 제안, 요구사항을 정리한 문서.

---

## 1. 한 줄 정의

> **pit는 기획/아이디어/결정/체크리스트를 Git처럼 버전 관리하고,
>  git에 존재하는 실제 코드와 비교하여
>  "현재 기획 대비 개발 정합도"를 평가·시각화해주는
>  아이디어/기획 버전 컨트롤 & PM 관제 시스템이다.**

---

## 2. 배경 및 문제 정의

### 2.1 현재 상황

작은 회사, 작은 팀에서도 실제 개발 프로세스는 점점 복잡해지고 있다.

**기획/아이디어/결정은:**
- ChatGPT·Claude 대화 로그
- Notion/Google Docs 문서
- 로컬 `.md` 파일
- 회의/슬랙/음성 대화

에 흩어져 있다.

**개발은:**
- 여러 Git 레포
- 여러 브랜치 전략
- CI/CD 파이프라인
- 마이크로 서비스(MSA) 구조

위에서 진행된다.

### 2.2 반복되는 질문들

**대표/PM/기획자:**
- "그때 이거 왜 이렇게 하기로 했더라?"
- "기획 문서는 어디 있었지?"
- "이 기능, 지금 개발이 얼마나 된 거야?"

**개발자:**
- "이 코드는 대체 어떤 의도로 짰던 거지?"
- "이 기능은 어느 기획 문서를 봐야 하지?"
- "새로 합류했는데, 서비스 전체의 맥락을 어디서 잡지?"

### 2.3 기존 도구의 한계

| 도구 | 강점 | 한계 |
|------|------|------|
| **Git** | 코드와 히스토리 관리 | "왜 이렇게 만들었는지(의도/결정/기획)" 표현 어려움 |
| **Jira/Linear** | 티켓/스프린트 관리 | LLM 기반 기획 내용 구조화 어려움, spec–code 정합도 미지원 |
| **Notion/Confluence** | 문서/회의록 보관 | "현재 코드와 얼마나 맞는지" 관점 약함 |

### 2.4 LLM 기반 개발 시대의 문제

- ChatGPT/Claude와의 대화 속에서 **"사실상 기획·설계·결정의 70% 이상"**이 이루어지는데,
- 이 결과물이 **어디에도 SSOT(Single Source Of Truth)로 남지 않는 문제**가 생긴다.

## 3. 타깃 사용자

### 3.1 1차 타깃

- **소규모 팀(1~7인)의 대표 / PM / 기획자**
  - 직접 기획/설계를 하고 LLM과 대화하며 프로젝트를 끌고 가는 사람
  - Notion, ChatGPT, GitHub를 병행 사용하지만 SSOT가 없어 괴로운 사람

- **풀스택/리드 개발자**
  - Git/CLI에 익숙하고, "티켓 시스템은 너무 무겁다"고 느끼는 사람
  - 브랜치/PR/커밋을 기획 단위로 관리할 수 있다면 좋겠다고 느끼는 사람

### 3.2 2차 타깃

- 외주/프리랜서와 협업이 잦은 팀
- 연구개발 프로젝트(논문/프로토타입)와 제품개발이 섞여 있는 팀
- MSA 환경에서 여러 마이크로 서비스를 관리하는 플랫폼 팀

## 4. 핵심 컨셉

### 4.1 데이터 단위

pit는 다음 네 가지 단위를 핵심으로 삼는다:

| 단위 | 설명 | ID 예시 |
|------|------|---------|
| **Project** | 하나의 제품/서비스/시스템 | `pit`, `slam`, `pios` |
| **Feature** | 기획/개발/테스트/배포가 한 덩어리로 움직이는 작업 단위 | `F-0001`, `F-INC-0003` |
| **Decision** | "왜 이렇게 했는지"를 남기는 문서 | `D-0001` |
| **Log** | LLM/사람과의 기획 대화, 회의 내용 요약 | `2025-12-12-session-001` |

### 4.2 pit-flow (상태 흐름)

Feature는 다음과 같은 상태 흐름을 가진다:

```
planned → in_progress → ready_for_merge → merged → released
```

| 상태 | 의미 |
|------|------|
| `planned` | 기획 완료, 개발 시작 전 |
| `in_progress` | 브랜치 생성, 개발 진행 중 |
| `ready_for_merge` | 구현/테스트 완료, PR 열림 |
| `merged` | main/release 브랜치에 반영 |
| `released` | 실제 배포 완료 |

PM/기획자는 **이 상태와 체크리스트만 보면 된다.**
브랜치 전략, 머지 전략, 커밋 그래프 등 git의 기술적 디테일은 pit 뒤로 숨긴다.

### 4.3 정합도(Alignment) 신호

pit는 **현재 git 상태와 pit에 정의된 기획/요구사항 간의 "정합도"를 평가**한다.

**원칙:**
- 정합도는 **"절대적인 판결"이 아니라 "리스크 신호등"**이다
- 항상 **근거(왜 그렇게 판단했는지)**를 함께 제공한다

| 신호 | 의미 |
|------|------|
| **Green** | 기획 대비 구현이 잘 맞아 보임 |
| **Yellow** | 일부 요구사항/테스트 부족, pit 업데이트 필요 |
| **Red** | Acceptance Criteria 미충족, 관련 코드/테스트 부족, 장애 지속 |

## 5. 가치 제안

### 5.1 기획자/대표 관점

- "내가 ChatGPT/Notion에서 만든 기획/결정들이 Feature/Checklist 기준으로 잘 정리되어 있고 Git과 연결되어 있다."
- "프로젝트 상태/헬스를 한 눈에 볼 수 있다."
- "새 개발자에게 pit만 보여줘도 온보딩 이야기가 줄어든다."

### 5.2 개발자 관점

- "Jira/대형 이슈 트래커 없이도, Feature ID(F-0001)를 기준으로 브랜치/PR만 잘 써도 기획과 상태를 맞춰갈 수 있다."
- "기획자가 만든 체크리스트와 요구사항을 CLI에서 바로 볼 수 있다."

### 5.3 팀 관점

- "Incident/VOC, 큰 결정, 각 Feature의 요구사항/수용기준이 한 구조 안에서 관리된다."
- "각 프로젝트별로 '지금 무엇이 중요한지'를 공유하기 쉽다."

## 6. 주요 시나리오

### 시나리오 1: 새 기능 기획 & 개발

1. 대표/기획자와 LLM이 대화: "SLAM의 Active Learning v2 설계하자."
2. 대화 끝에서: "이제 pit에 F-0001로 정리해줘."
3. LLM이 Feature yaml + Decision + Log 생성 → pit 레포에 저장
4. 개발자는 `pit feature checkout F-0001` (브랜치 생성)
5. pit는 체크리스트 + git 상태를 기반으로 진행도/정합도 표시

### 시나리오 2: VOC/긴급 장애 대응

1. 고객 VOC/모니터링 알람: "결제가 안 된다."
2. PM이 Incident Feature 생성: `F-INC-0003 – 2025-12-12 결제 장애`
3. 개발자는 urgent Task만 필터링해서 핫픽스 작업
4. PR 머지 + 모니터링 정상화 후 → Task 완료 처리

### 시나리오 3: 프로젝트 헬스 확인

1. PM이 `pit health project pit` 실행
2. Green/Yellow/Red Feature 리스트 확인
3. Yellow/Red에 대해 원인 파악, 우선순위 조정

## 7. 제품 요구사항

### 7.1 기능 요구사항 (FR)

**Project/Feature/Checklist 관리:**
- [FR-01] 프로젝트 생성/조회/수정 (파일 기반)
- [FR-02] Feature 생성/조회/수정 (id, title, status, type 등)
- [FR-03] Feature 내 체크리스트(Task) 관리

**Git 연동:**
- [FR-10] `.pit.yml` 기반 코드 레포 ↔ project_id 연결
- [FR-11] Feature ID 기준 브랜치 생성
- [FR-12] 현재 브랜치/PR URL을 Feature에 기록
- [FR-13] Git 상태 요약 (최근 커밋, PR 상태, CI 결과)

**헬스/정합도:**
- [FR-20] Feature 단위 헬스 상태 계산
- [FR-21] Project 단위 헬스 요약 (Green/Yellow/Red)
- [FR-22] 헬스 판단 설명/제안 제공

**Incident/VOC:**
- [FR-30] Incident 타입 Feature 생성/관리
- [FR-31] urgent Task 표시
- [FR-32] Incident 관련 헬스 상태 별도 표시

**CLI/TUI:**
- [FR-40] `pit` CLI: 프로젝트/Feature/Checklist/헬스 조회/조작
- [FR-41] `--json` 출력 옵션 (에이전트/툴 재사용 가능)
- [FR-42] (이후) Textual 기반 TUI

### 7.2 비기능 요구사항 (NFR)

| 영역 | 요구사항 |
|------|---------|
| **사용성** | CLI 명령은 git/poetry/kubectl 패턴을 따름 |
| **성능** | 수백 개 Feature, 수천 개 Task까지 체감 지연 없이 조회 |
| **확장성** | 추가 필드를 넣기 쉽되, 기존 필드와 호환성 유지 |
| **보안** | pit 자체는 API 키/비밀번호 저장하지 않음 |

## 8. 범위 및 릴리즈 계획

### 8.1 In-Scope

- 파일 기반 Project/Feature/Decision/Log 구조 및 파서
- Feature/Checklist 중심 개발 플로우
- CLI 중심 조작
- Git 브랜치/PR/커밋과 Feature ID 연결
- 기본적인 헬스/정합도 평가 (규칙 기반)

### 8.2 Out-of-Scope (초기 버전)

- Jira/Linear 같은 풀 스케일 이슈 트래킹 대체
- LLM 에이전트 완전 자동화
- Vault 수준의 시크릿/키 관리
- 멀티테넌트 SaaS
- 복잡한 역할/권한(ACL) 관리

### 8.3 릴리즈 계획

| 릴리즈 | 목표 |
|--------|------|
| **R0** | 설계 문서 정리 완료 (현재 단계) |
| **R1** | CLI 중심 로컬 도구 (MVP) – 파일 기반, 기본 git 연동 |
| **R2** | 헬스/정합도 + TUI – SQLite 인덱스, Textual TUI |
| **R3** | 에이전트/LLM 연동 – MCP 또는 별도 API |

## 9. 성공 기준

### 9.1 정량 지표

- 하나의 실제 프로젝트에서:
  - pit에 기록된 Feature가 **10개 이상**
  - Incident Feature가 최소 **1건 이상** 사용
  - `pit` CLI를 **일주일에 20회 이상** 실행
- 새로 합류한 팀원이 pit만 보고 프로젝트 이해하는 시간 **30% 이상 감소** 체감

### 9.2 정성 지표

- 대표/PM: "예전처럼 '문서 어딨어?'라는 말을 덜 하게 되었다"
- 개발자: "Jira/Notion 대신 pit Feature ID만으로도 브랜치/PR 관리가 편하다"

## 10. 리스크 및 안티 패턴

### 10.1 리스크

| 리스크 | 해소 전략 |
|--------|---------|
| 새로운 "관리 지옥"이 될 위험 | SSOT 역할을 pit에 집중, 다른 툴은 보조로만 |
| 문서 작성 부담 증가 | PM/대표가 먼저 사용, CLI/에이전트로 작성 피로도 감소 |
| LLM/에이전트 의존성 증가 | core pit는 LLM 없이도 완전 동작하도록 설계 |

### 10.2 안티 패턴

- pit를 **Jira/Notion/Confluence 전부를 대체하는 툴**로 착각
- Project/Feature 단위를 흐리게 쓰는 것
- Feature/Task ID 없이 브랜치를 마음대로 파고, 나중에 pit에 "대충 맞춰 끼우려는" 방식

---

## 11. 핵심 철학

> **"문서는 LLM이 쓰고, 사람은 피드백만 한다."**

pit의 근본 철학:
- 포맷/파일/폴더/ID/인덱싱 → **LLM + pit 시스템의 책임**
- 사람은 → **"이 내용이 지금 맞냐/틀리냐"만 판단**

목표는:
> **사람이 "복붙·정리 노동"에서 최대한 해방되는 방향**

pit는 **"문서 더 쓰게 하는 도구"가 아니라,
"이미 LLM과 대화로 쓰고 있는 문서를 덜 귀찮게 정리·추적·연결해주는 도구"**가 되어야 한다.
