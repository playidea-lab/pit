# .pit/ 폴더 기반 로컬 프로젝트 관리 방식 채택

## 배경

기존에는 `projects/<project_id>/` 중앙 저장소 방식으로 여러 프로젝트를 관리했으나,
사용 시나리오가 불명확했음:
- MCP에서 "pit 프로젝트에 추가해줘" → pit이 뭔지 어떻게 알지?
- CLI로 실행할 때 git처럼 "현재 폴더 기준"으로 동작해야 하지 않나?

## 결정

**git처럼 `.pit/` 폴더 방식 채택**

```
my-project/
├── .git/           ← git 저장소
├── .pit/           ← pit 저장소
│   ├── config.yaml
│   ├── features/
│   ├── decisions/
│   └── logs/
└── src/
```

## 이유

1. **직관적**: `.git/`이 있으면 git repo, `.pit/`이 있으면 pit project
2. **독립적**: 각 프로젝트가 자체 기획 데이터 소유
3. **컨텍스트 자동 감지**: 현재 폴더 기준으로 동작
4. **git과 함께 버전 관리**: `.pit/` 폴더도 git으로 추적 가능

## 대안 검토

| 방식 | 장점 | 단점 |
|------|------|------|
| 중앙 저장소 | 여러 프로젝트 한 곳 관리 | 컨텍스트 불명확, 실제 코드와 분리 |
| `.pit.yml` 파일 | 가벼움 | 데이터 저장 위치 모호 |
| **`.pit/` 폴더** | git과 동일한 패턴, 직관적 | 폴더 하나 추가 |

## 영향

- `pit init` 명령어 추가
- `project_id` 파라미터 선택적으로 변경
- 기존 `projects/` 방식도 하위호환 유지
